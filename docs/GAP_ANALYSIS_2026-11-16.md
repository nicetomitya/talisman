## 2. Целевая архитектура

Модульный монолит сохраняется. Новые модули:

* `src/server/domain/crm.ts` — контакты, импорт, задачи, тексты, приглашение и связывание, показатели.
* `src/server/domain/cabinet.ts` — полисы вне платформы, проверка рынка, разбор страхового случая.
* `src/server/domain/commissions.ts` — происхождение сделки, спор и решение.
* `src/server/domain/requests.ts` — источник заявки, защита от дублей.
* Машины состояний `crmLink` и `commission` в `src/server/state/machines.ts`.

## 3. Пользовательские сценарии

**Агент и своя база.** CSV или ручной ввод → карточки «не приглашён» (аккаунты не создаются, писем нет) → задачи на продление за 30 дней → помощник готовит текст, агент отправляет сам и записывает в историю.

**Приглашение.** Агент: «Подготовить приглашение» → одноразовая ссылка (30 дней) и текст → отправил сам → «Отметить отправленным». Клиент: ссылка → вход или регистрация → «Принять» (registered_unverified) → «Мои агенты»: подтвердить (если email или телефон совпадает) с переносом полисов или без, либо отклонить. Позже — «Отозвать доступ».

**Новая потребность импортированного клиента.** Заявка открыта всем подходящим агентствам. Победило другое агентство — обычная доля платформы; снова выбран пригласивший — пониженная (U12).

**Страховой случай.** «Меня затопили соседи» на главной → `/c/claims/new` → подходящие полисы с объяснением, первые шаги, доказательства, сроки, оговорка → обращение по полису платформы или инструкция по внешнему полису.

**SEO.** `/guides/<slug>` → «Разобрать мою ситуацию с AI» → `/c/requests/new?text=…&src=seo:<slug>` → `InsuranceRequest.sourceDetail` → `/admin/funnel`.

## 4. ERD (новое и изменённое)

```
Organization 1─* CrmContact *─0..1 User (linkedUserId, только после подтверждения клиентом)
CrmContact 1─* CrmPolicy ─0..1 ExternalPolicy (crmPolicyId, если клиент перенёс полис)
CrmContact 1─* CrmInteraction
CrmContact *─1 CrmImportBatch (importBatchId)
Task (relatedType = "CrmContact", relatedId)
User 1─* ExternalPolicy (source CLIENT_MANUAL | AGENT_CRM, verification)
User.acquisitionSource / acquisitionOrgId       — источник клиента
InsuranceRequest.source / sourceOrgId / sourceDetail — источник заявки
Commission.dealOrigin / disputeReason; kind DISPUTE_REVERSAL
Consent(purpose = AGENT_LINK, recipients = orgId)
```

Инварианты в БД: UNIQUE `(organizationId, emailNorm)`, `(organizationId, phoneNorm)`, `(organizationId, linkedUserId)`; CHECK «связанная карточка имеет linkedUserId»; FK на организацию и пользователя.

Сопоставление сущностей дополнения: `ClientAgentRelationship` = связанная `CrmContact` + `Policy.agencyOrgId` (отдельная таблица не нужна в P1-A); `RFQInvitation` = `Auction.eligibleOrgIds`; `Match/Application` = `Checkout`; `BillingEvent` = `Commission`; `Claim/ServiceCase` = `Claim` (для внешних полисов обращение пока не создаётся, ⏳).

Сопоставление статусов: RFQ draft/confirmed/matching/offers_received/selected/application/issued ↔ `DRAFT`/`NEEDS_INFO`/`OPEN`/`SELECTION`/`CHECKOUT`/`COMPLETED`; Offer ↔ `QuoteStatus`; Policy ↔ `ContractStatus` + «скоро окончание» по дате; Billing ↔ `ACCRUED`/`CONFIRMED`/`RECEIVED`/`REVERSED`/`DISPUTED`.

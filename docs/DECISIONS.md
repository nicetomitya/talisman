# Журнал решений и неопределённостей

Рутинные решения приняты самостоятельно в рамках ТЗ. Пункты, затрагивающие право, деньги, документы и данные, — **ограничения P0, которые нужно снять до P1**, а не молчаливые допущения.

## Архитектура

| # | Решение | Почему |
|---|---|---|
| D01 | Модульный монолит: Next.js 15 (страницы + API) и отдельный процесс worker на одной БД | Минимум движущихся частей для P0, границы модулей сохранены в `src/server/domain/*` |
| D02 | Очередь заданий в PostgreSQL (`Job`, `FOR UPDATE SKIP LOCKED`), outbox и inbox вебхуков | Задания, дедлайны и идемпотентность переживают рестарт (AC07, AC33) без отдельного брокера |
| D03 | Демочасы — смещение в таблице `Setting`, общее для сервера и worker | Можно «перемотать» к окну события, не трогая системное время |
| D04 | Собственные сессии в БД, Argon2id, TOTP для сотрудников, CSRF double-submit + проверка Origin | Без внешних провайдеров авторизации и ключей |
| D05 | Обновление интерфейса опросом (4 с), а не WebSocket | Проще, сервер всегда отдаёт актуальный снимок; таймер торгов считается по серверному времени |
| D06 | Адаптеры за реестром: в demo — эмуляторы, в production — заглушка, бросающая `INTEGRATION_NOT_CONFIGURED` | Демо-ответ не может «утечь» в боевой режим (AC34) |
| D07 | Деньги — целые копейки, проценты — базисные пункты, погода — целые сотые | Без плавающей точки, детерминированные расчёты |
| D08 | Инварианты дублируются в БД: частичные UNIQUE-индексы (одна активная версия предложения, один резерв), CHECK на лимит выплат | Защита от гонок, а не только от ошибок кода |
| D10 | Выбор предложения — «матч»: торги закрываются, остальные предложения истекают, их агентства получают нейтральное уведомление и теряют доступ к заявке; чат и данные клиента — только у выбранного агентства. Отменить матч можно до оплаты, после этого заявка закрыта, клиент создаёт новую — всем или напрямую тому же агентству | Решение владельца от 02.11.2026: понятная модель «как матч», без возврата к прежним предложениям |
| D11 | Сроки и фиксированные условия: подбор 24 ч; улучшение в последние 15 мин продлевает на 15 мин, всего ≤ 1 ч; после матча 2 ч на ознакомление, подпись и оплату (напоминания за 60 и 15 мин), иначе матч завершается. После подачи агентство может только снизить цену при тех же условиях; отозванное предложение повторно не подаётся. Контакты сторон скрыты, в чате телефоны, почта, ссылки и ники заменяются пометкой. ИИ-помощник (эмулятор) подсказывает клиенту полноту заявки и даёт агентству разбор с коридором цены по тарифу, ничего не меняя сам | Решение владельца от 03.11.2026: без торга после подачи, общение только через платформу |
| D12 | Дополнение ТЗ от 16.11.2026 внедряется эволюционно, без переписывания P0: новые таблицы CRM и внешних полисов, nullable-колонки атрибуции; миграция обратима (`down.sql`). Названия статусов P0 сохранены, соответствие статусам нового ТЗ — в `docs/GAP_ANALYSIS_2026-11-16.md` | Требование ТЗ: «сохранять реализованное», «обратимая миграция» |
| D13 | `CrmContact` ≠ `User`. Связь только по персональной одноразовой ссылке, действием клиента и при совпадении подтверждённого email/телефона аккаунта с каналом в карточке; при несовпадении — отказ, без автоматического слияния. Заметки и история агентства клиенту не показываются. Клиент может отозвать связь (согласие `AGENT_LINK` отзывается) | ТЗ 16.11, пп. 6.2, 6.3, 9.1, 10 |
| D14 | Платформа не отправляет приглашения и сообщения контактам CRM: помощник готовит текст, агент отправляет его сам и отмечает канал | ТЗ 16.11, п. 6.2: «не отправлять автоматически без правовых оснований и подтверждения» |
| D15 | Новая потребность всегда — новый открытый подбор для всех подходящих агентств; прежний или пригласивший агент участвует на равных. Заявка лично агентству — только явным действием клиента («повторить тому же агентству», D10) | ТЗ 16.11, пп. 1, 5.2, 9.1 |
| D16 | Источник клиента (`User.acquisitionSource`, пишется один раз) и источник заявки (`InsuranceRequest.source`, `sourceDetail`) хранятся раздельно. «Приглашён агентством» фиксируется только для нового клиента без заявок и полисов | ТЗ 16.11, п. 9.1 |
| D17 | Защита от спама без платного поиска: одна активная заявка на объект (VIN / адрес / бронирование) и дату начала; лимиты частоты уже были | ТЗ 16.11, п. 7.2 |
| D18 | Начисления получили машину состояний `commission` (в т. ч. `DISPUTED`); спор открывает владелец агентства, решает администратор; признанный спор — отдельная запись сторно `DISPUTE_REVERSAL` | ТЗ 16.11, пп. 12, 14 |
| D19 | ТЗ v2 (21.11.2026) — новая база продукта: US-first Event Risk Marketplace на английском, USD. Реализован этап P1 «Event-first Demo» только в симуляции. Русский страховой контур (P0, P1-A) не удалён, переведён в legacy: `/insurance`, `/c`, `/a`, `/admin` | ТЗ v2, пп. 0, 2, 16 |
| D20 | Деньги — целые центы, цена доли 1..99 центов за выплату $1, пороги — целые сотые, вероятности — базисные пункты. Даты события — локальные дни + IANA timezone; UTC = начало первого дня и начало дня после последнего в этом поясе | ТЗ v2, п. 13.3, крит. 2 |
| D21 | Лимиты симуляции — продуктовые гипотезы: T0 $1k (гость, только расчёт), T1 $5k, T2 $25k (одобренный эксперт), T3 $100k (только админ). Лимит — суммарная возможная выплата всех лотов по `eventRootKey` | ТЗ v2, п. 9.3, крит. 18 |
| D22 | Talisman не берёт комиссию ($0). Комиссия симулированной площадки — иллюстрация ($0.01 за 10 долей), подписана как ненастоящая | ТЗ v2, п. 12, крит. 22 |
| D23 | Позиция хранится лотами (одна на исполненный бумажный ордер). Бумажное исполнение не сдвигает демо-стакан (воспроизводимость) | Простота и детерминизм демо |
| D24 | Котировка живёт 60 с (по демо-часам); подтверждение только по свежему снимку с текущим `termsHash`. Смена условий рынка — новая версия и новый hash, старые котировки и сопоставления требуют пересмотра | ТЗ v2, крит. 7, 25 |
| D25 | Исход: наблюдения основной станции, пропуски — резервной; если данных нет — NEEDS_DATA и никакой выплаты. Предложенный исход имеет окно спора (48 ч, стройка — 168 ч); подтверждает администратор; расчёт идемпотентен | ТЗ v2, пп. 7.3, крит. 14, 15 |
| D26 | Гость может описать риск, уточнить, подтвердить и смотреть котировки; черновик привязан к httpOnly-cookie (в БД только хэш) и переходит в аккаунт при входе. Бумажные позиции — только после входа | ТЗ v2, п. 10.2 |
| D27 | Рынок на конкретную стройку — RESTRICTED + manipulation risk: позиция только после декларации связи; сотрудник, подрядчик, инспектор — запрет; аффилированные и «другое» — ручная проверка. Пользователь не может сам смягчить ограничение | ТЗ v2, п. 9.4, крит. 16 |
| D09 | Название механизма в коде — reverse auction; в интерфейсе — «предложения», «улучшение», без «ставок» и обратных отсчётов, давящих на клиента | Требование ТЗ |

## Решения по ходу реализации

* TypeScript закреплён на 5.9.3: TypeScript 7 ломает загрузку `next.config.ts`.
* `reset-demo` = `prisma migrate deploy` + сид; сид сам очищает данные (TRUNCATE) и заполняет их через доменные операции, поэтому результат воспроизводим.
* Серверные компоненты не передают функции в клиентские; переходы после действий задаются шаблонами вида `/c/claims/{claimId}`.
* Наблюдения погоды общие для станции и окна, поэтому в тестах каждый случай использует свою дату события.
